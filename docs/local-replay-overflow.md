# 多页签历史回放与发送队列

2026-10-26；独立连接修复，以已发布 Windows 0.2.47 源码为基线。

## 已复现的问题

本机 6769 daemon 和 6771 界面代理的 HTTP 检查均返回 200，新 WebSocket
连接可正常鉴权。只订阅一个会话可以正常回放；同时订阅六个本机页签时，
daemon 在第一份快照之后主动以 1013 断开，原因是发送队列溢出。代理随后
报告本机后台连接结束。该证据排除了“本机端口没有监听”这一解释。

原实现把新增页签快照一次排入同一个实时输出队列。每次发送快照之后，
还要等待可选的控制台底栏读取。在这个等待期间，其他活跃会话的输出继续
排队。反复刷新会进一步累积快照；仅扩大队列无法解决慢读取造成的阻塞。

## 修复约束与验收

- 历史回放应按可用容量分批调度，保留实时输出空间，重复刷新合并。
- 读取底栏不得阻塞正常输出。后台读取须有并发上限；旧结果不能覆盖新输出，
  不能越过撤销的授权、已变化的会话或终端尺寸。
- 不丢弃正常实时字节，不降低鉴权要求，不把队列改成无界。
- 兼容旧 daemon 的代理按顺序请求回放，并确认前一批已排空；显式刷新不能
  通过临时取消订阅实现，以免释放其他客户端正在使用的尺寸控制权。
- 验收包括 16～40 个自有会话、小队列、慢底栏、重复刷新、实时帧顺序、
  断开清理、尺寸控制权和无效 Token 拒绝。

## 应用范围

现有终端进程在诊断期间保持运行。界面代理可以缓解旧后台的一部分回放
突发，但无法改变旧后台内部等待底栏的发送逻辑。完整修复需要后台使用
新代码；替换正在运行的 daemon 会影响其持有的 PTY，因此不能把“更新了
客户端外壳”当成“现有后台已经修复”。应用前应保留用户对会话中断的决定。

此前暂停的配色、剪贴板、中央 mylib 和 Android 开发不属于本次隔离版本。

## 验证记录

- 联合回归：136 项测试、14 项子测试通过；线程异常视为错误，无警告。
- 40 个自有会话的真实回环直连／中继、小队列、重复刷新及取消验证通过。
- 持续实时输出下，新窗口回放可以公平推进，不会永久停在空白状态。
- 16／40 个空闲窗口最终均可恢复底栏；真实读取并发始终不超过四个，
  待处理记录为小型身份信息，不保存整份大快照，最多 256 项。
- 编译版已在隔离后台运行 16 个真实 ConPTY，每个写入 3,000 行，四轮
  每轮回放 4,194,144 字节，16 个输入回显均收到，未出现队列溢出。
- 编译包中 41 个程序模块逐一与隔离源码比对，未混入主工作区的未完成功能。

队列仍有内存上限：确实无法及时接收实时流量的客户端会明确断开，不静默
丢弃实时字节。40 个窗口的回放验证不代表任意无限速实时输出也能零断线。
